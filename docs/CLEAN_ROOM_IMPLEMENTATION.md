# 독립 구현(clean-room) 정책 / Independent implementation policy

**ACTIVE · 2026-10-31 · 적용 범위: 외부 저장소의 기능·기술을 TalkAbout 자체 로직으로 재구현할 때**

이 문서는 "라이선스가 문제 되는 기술을 다른 로직으로 구현"하는 절차와 경계를 정한다.
**법률 자문이 아니며**, 상업 배포·대규모 기능 재현 전에는 별도 법률·특허 검토가 필요하다.

## 1. 원칙

저작권은 **표현(코드·주석·문자열·표·문서·asset)** 을 보호하고, 아이디어·기능·알고리즘 자체는 원칙적으로 보호하지 않는다.
따라서 **공개 문서·관찰 가능한 동작·표준/프로토콜 사실만으로 자체 구현**하는 것은 정당한 방법이다. 반면 다음은 금지한다.

- 코드·주석·문자열·상수표·fixture·UI 문구·문서 문장·asset의 **복사·번역·개작**
- 파일·함수·자료구조를 **1:1로 옮기는 것** (파생물 위험이 높다)
- 상표(제품명·로고) 사용, 검증 없는 **호환성·공식 지원·인증 주장**
- 특허 침해: 독립 구현이라도 특허는 별개다. **상업 배포 전 특허 검토**가 필요하다.

## 2. 라이선스별 판단

| 라이선스 | 코드 사용 | 독립 구현 | 유의 |
| --- | --- | --- | --- |
| MIT / Apache-2.0 | 가능(고지 의무) | 가능 | 이 프로젝트는 **코드 복사보다 독립 구현을 기본**으로 한다. Apache는 NOTICE·특허 조항 검토 |
| GPL-2.0/3.0 | 결합·배포 시 전염 위험 | **가능**하되 "독립성" 입증 필요 | 코드를 읽고 베끼면 파생물. 코드 없이 문서·동작만으로 설계하고 diff를 검토한다 |
| AGPL | 네트워크 제공 시 소스 공개 의무 | 가능(동일 원칙) | 네트워크 서비스 형태 배포 시 특히 보수적으로 |
| PolyForm Noncommercial | 비상업 한정 | **가능**(기능 재구현은 별개) | 그들의 소프트웨어·asset·문서를 사용·복사하지 않는다. 이름·상표 금지 |
| 별도 asset 라이선스(폰트·아트) | 별도 조건 | 대상 아님 | **asset은 재현 대상에서 제외**한다 |

## 3. 필수 절차

1. **스펙 분리**: 공개 문서·관찰 가능한 동작·표준 사실만으로 요구사항을 쓴다. 상대 코드의 "번역"이 아니라 **요구사항 재작성**이어야 한다.
2. **구현 분리**: 스펙만 보고 자체 네이밍·자료구조·에러 어휘로 구현한다. 상대의 파일 구조·함수 분해·상수·에러 문자열을 따르지 않는다.
3. **테스트 분리**: 상대 저장소 fixture를 복사하지 않고 **자체 synthetic fixture**를 만든다.
4. **기록**: 참조 revision·라이선스, 참고한 것(문서/동작), 자체 설계 요점, 복사하지 않았음을 PR·문서에 남긴다.
5. **검토**: 기능 동등성이 **구조 동등성**으로 흐르지 않았는지 diff를 리뷰한다. GPL/NC 대상이면 더 보수적으로.
6. **주장 금지**: 호환·인증·성능 동등을 실제 시험 없이 표기하지 않는다. 미실행은 **NOTRUN**으로 적는다.

## 4. 기록 템플릿 (PR 설명 또는 설계 문서에 복사)

| 항목 | 값 |
| --- | --- |
| 참조 저장소 / revision | `owner/repo@sha` |
| 참조한 것 | 공개 문서·관찰 가능한 동작·표준 사실 |
| 복사하지 않음 확인 범위 | 코드·테스트·fixture·문구·asset |
| 자체 설계 요점(상대와 다른 점) | 네이밍·구조·검증 방식 등 |
| 검증 | 합성 테스트/실행 결과, NOTRUN 목록 |
| 특허·상표 검토 필요 | 예/아니오 + 사유 |

## 5. TalkAbout 적용 현황

- **2026-10-31 반영분**: P0-1(관측 실패≠허용), P0-2(exec schema fixture), P0-3(승인 데이터 계약), P0-4(격리·placement 계약표)은 이 정책에 따라 **설계 참조 + 자체 작성**으로 반영했다. 외부 코드·문장·asset은 포함하지 않았다.
- **첫 독립 구현 사례**: W1 workspace 경로 경계의 **최종 구성요소 junction/reparse 거부**. 이는 serena·munder-difflin이 쓰는 "경로 봉쇄" **개념**을 자체 로직으로 구현한 것이며 해당 코드를 복사하지 않았다. 중간 구성요소는 여전히 `resolve()`로 해석되며 이는 sandbox가 아니다.
- **두 번째 독립 구현 사례(2026-10-31)**: `GET /rooms/{id}/diagnostics`의 read-only 대기 사유 투영([observation.py](../talkabout/observation.py)). openbot의 "보류 사유 표시", rakazo의 "자원 대기와 사람 대기 구분", open-duet의 "read-only 진단"에서 **문제 정의만** 참고했고, enum 이름·규칙·응답 구조·테스트는 이 저장소에서 새로 설계했다. 아래 기록 표에 실제 값을 채웠다.

| 항목 | 값 |
| --- | --- |
| 참조 저장소 / revision | openbot `fde32512…`, rakazo `1ab3a840…`, open-duet `87d71d70…` (고정 SHA) |
| 참조한 것 | 공개 문서·관찰 가능한 제품 동작(대기 사유를 사용자에게 보여준다는 문제 정의) |

## 6. 근거와 한계

- 저장소별 고정 revision·라이선스는 [2차 분석 소스 원장](../analysis/repo-review-2026-10-31/00-SOURCE-MANIFEST.md), 외부 참고 기록은 [SOURCES.md](SOURCES.md)에 있다.
- 이 정책은 **위험을 낮추는 실무 규칙**이며, 독립 구현이 항상 무위험임을 보장하지 않는다. 분쟁 가능성이 있는 기능은 착수 전 법률 검토를 받는다.
- 코드가 실제로 자체 작성되었는지의 최종 판단은 사람 리뷰(파일 이력·diff)로 한다.
