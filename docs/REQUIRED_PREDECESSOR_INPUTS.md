# 필수 선행 결과 입력 계약

이 문서는 로컬 작업 트리 기준입니다. 배포·실제 provider 호출·격리 PostgreSQL 동시성 검증을 의미하지 않습니다.

## 계약과 실행 경계

사람이 소유한 작업 계획의 각 노드에 선택적으로 `required_predecessors`를 지정할 수 있습니다. 값은 해당 노드 `depends_on`의 중복 없는 부분집합이며, 각 ID는 같은 실행(run)의 선행 노드 **결과 메시지 전체**를 뜻합니다. 필드가 없는 기존 계획은 이전처럼 best-effort 전달을 사용합니다. 빈 배열도 명시된 계약이며 파일·산출물 버전 전달 계약은 아닙니다. 저장이나 제안의 승인 자체는 실행을 시작하지 않습니다.

서버는 정확한 선행 결과 바인딩과 현재 수신자의 접근 가능성을 노드 배정·실행 승인 시 검사합니다. 계약을 지원하지 않는 워커는 거절됩니다. 호환 워커는 실제 준비한 문맥의 필수 메시지를 fit 이후 검사하며 누락되거나 잘렸으면 provider 호출 전에 멈춥니다. 준비 입력 manifest는 워커의 보고를 서버가 참조·범위·바이트 동일성에 대해 검증한 것이지 모델의 수신·이해·정확성을 증명하지 않습니다. 특히 `message`와 `artifact_version` 참조의 SHA-256은 보고된 범위가 실제 서버 내용과 **바이트 단위로 같다**는 것만 증명하며, 전달(delivery)이나 모델의 이해·활용을 증명하지 않습니다. manifest가 있으면 두 종류의 참조에 대해 SHA-256이 필수이고, 불일치·누락은 `invalid_input_source`(422)입니다. manifest가 없는 legacy 완료 보고는 기존처럼 `legacy_input_unverified`로 기록됩니다. 악의적인 클라이언트의 외부 호출이나 허위 보고까지 막는 샌드박스가 아닙니다.

현재 워커는 필수 결과를 최대 8개(`REQUIRED_PREDECESSOR_LIMIT`)까지 준비합니다. 이 한도는 워커가 claim 시 `required_predecessors_limit`로 협상하는 capability이며, 서버는 요청마다 1..15 범위만 받습니다. 노드의 실제 필수 결과 수보다 작거나 필드가 없으면 서버는 lease를 주지 않고 해당 노드를 `input_unavailable`로 조기에 실패시킵니다(409 `required_input_unavailable`). 이 실패는 lease 이전에 확정되므로 워커는 이를 로컬 `failed`(`error_code=required_input_unavailable`, `input_failure_report=server_rejected_claim`)로 종료하고 불확실로 멈추지 않습니다. API는 최대 15개를 저장할 수 있으므로 8개를 초과하는 계약은 현재 워커에서 실행되지 않으며, 서버는 8을 정책값으로 고정하지 않고 오직 협상된 값과 계약 크기를 비교합니다. 필수 결과가 너무 크거나, 권한·이력 경계가 바뀌어 볼 수 없거나, 직렬화 예산에 들어가지 않아도 실행할 수 없습니다. 실패 원인은 일반적인 입력 불가로 표시하며 숨겨진 식별자를 공개하지 않습니다.

워커는 실행 시작 전 입력 불가를 로컬에 `failed`로 기록한 뒤 서버에 한 번 보고합니다. 이 보고는 최선 노력(best effort)이며 전송 오류(OSError/httpx 전송 오류)와 HTTP 5xx에 한해 같은 idempotency key로 최대 2회 더 재시도하고, 성공 또는 4xx 응답이면 즉시 중단합니다. 재시도해도 응답이 유실되면 결과는 불명이며 서버에는 lease 만료로 표시될 수 있습니다. 서버는 필수 프로토콜 계획 노드에 대해 lease가 만료되었거나 상태가 `queued`/`leased`/`expired`인 경우에도, attempt/generation/membership_revision·현재 assignee·필수 프로토콜 노드가 일치하고 `started`/`completed` 예약이 없으면 늦은 입력 불가 보고를 한 번 수용해 노드를 `failed`(`input_unavailable`)로 전환하고 실행을 조정합니다. 시작된 예약이 있으면 거절하며, 정상 fencing과 만료 동작은 다른 모든 verb에서 그대로 유지됩니다. 이 보고는 워커의 주장이지 독립적인 증거가 아닙니다. 운영자는 현재 실행과 워커 상태를 확인하고, 필요하면 입력 범위를 변경한 새 계획 revision을 작성하고 별도 dispatch해야 합니다. 결과가 불명확한 외부 실행은 자동 재시도하지 않습니다.

권한 재검사는 서버가 실행을 승인하는 시점까지의 검사입니다. 승인 이후 전달된 데이터는 회수할 수 없고, 이후 철회와 외부 provider 실행 사이의 경합을 제거하지 못합니다. `write_scope`는 강제 격리가 아니며 파일·도구·네트워크 격리나 금액 상한도 이 계약에 포함되지 않습니다.

## 남는 한계와 보완

- **모델 수신·이해는 증명할 수 없습니다.** SHA-256은 서버가 가진 바이트와의 동일성만 보장합니다. 실제 전달·이해를 증명하려면 provider 측 로그·감사·격리 실행 같은 앱 외부 수단이 필요합니다. 실행 영수증([EXECUTION_RECEIPTS.md](EXECUTION_RECEIPTS.md))은 provider 세션·응답 해시를 기록해 대조를 가능하게 하지만 증명은 아닙니다. 운영에서는 결과물 검토와 후속 질문으로 확인하세요.
- **보고 유실은 여전히 불명입니다.** 유한 재시도와 늦은 보고 수용으로 창을 줄였지만, 워커가 보고 전에 사망하면 서버는 lease 만료만 봅니다. 실행 상태를 새로고침해 확인하고, 자동 재시도는 하지 마세요.
- **회수 불가:** 승인 후 provider로 전달된 바이트는 되돌릴 수 없습니다. egress 허용목록, 워커 격리, 세션 종료 절차로 노출 범위를 제한하세요.
- **비용 상한 없음:** 서버는 provider를 호출하지 않으므로 비용을 집계하지 않습니다. provider 키별 쿼터·대시보드 경보와 워커의 `--max-model-calls` 같은 실행 예산으로 제한하세요.
- **적대적 클라이언트:** 프로토콜을 우회해 직접 provider를 호출하는 클라이언트는 이 계약으로 막을 수 없습니다. 신뢰 경계는 워커 실행 환경과 자격증명 관리에 있습니다.
