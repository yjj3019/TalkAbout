# 승인형 방별 메모리 / Room memory

**로컬 개발 중: 1단계 수동 미리보기만 구현 · 2~4단계 설계/미완료**

이 문서는 방별 메모리의 현재 경계와 후속 설계 관문을 구분한다. 후보는 메모리가 아니며, 미리보기는 승인·저장·주입을 수행하지 않는다. 이 문서는 배포나 운영 보존 정책의 승인이 아니다. **TalkAbout 방별 미리보기·실험 저장소는 Notion Memories/About 또는 다른 AI의 기억과 동기화되지 않으며, Notion MCP 연결·가져오기도 구현하지 않았다.**

## 1. 현재 구현: 사람이 요청하는 후보 미리보기

방 관리 화면의 **메모리 후보 미리보기**는 사람이 버튼을 눌렀을 때만 요청한다. 서버 경로는 `POST /api/v1/rooms/{room_id}/memories/preview`이며 본문은 빈 JSON 객체 `{}`다. 응답은 `preview_only`이고 `Cache-Control: no-store`가 적용된다. 미리보기는 서버에 후보를 저장하거나 이벤트를 추가하지 않고, 요약·재작성·모델 호출·첨부 본문 읽기·외부 전송을 하지 않는다. 승인이나 모델 입력 권한도 부여하지 않는다.

요청자는 현재 인증된 사람이어야 하며, 같은 workspace의 방에 활성 구성원으로 속하고 인증 범위와 구성원 권한 양쪽에 `room:read` 및 `room:control`이 있어야 한다. 방 범위 토큰 제약도 적용된다. 일반 human 인증은 세션을 사용하며 이 POST에는 같은 Origin과 CSRF 토큰이 필요하다. 테스트 전용 human bearer 허용을 일반 배포 권한으로 해석하지 않는다.

### 대상과 출력

- 요청자의 `read_start_seq` 이후 메시지 중 **human이 작성한 메시지**만 고려한다. 에이전트 메시지와 `attachment_refs`가 있는 human 메시지는 제외한다. 응답에 각각의 제외 개수를 표시한다.
- 이는 **완전한 첨부 유래 차단이 아니다**. 사람 메시지에 첨부 내용이나 다른 민감 자료가 복사·인용되어 있을 수 있고, 첨부 유래 여부를 판별하지 않는다. 첨부 본문을 직접 읽지 않는다는 사실도 모든 후보가 첨부 내용과 무관하다는 보장은 아니다.
- 동일한 원문 문자열만 반복 그룹으로 묶는다. 공백·줄바꿈·들여쓰기·대소문자·Unicode 표현이 다르면 다른 그룹이다. 빈 문자열과 최소 길이 검사는 별도 정규화로 수행한다.
- 최신 순으로 최대 50개 후보를 반환한다. 각 후보는 원문 또는 앞부분 최대 280자, 원문 출처의 메시지 ID·seq·작성자와 반복 횟수·출처를 담는다. 후보 발췌 총량은 최대 8,000자, 한 그룹에 표시하는 출처는 최대 20개다. 반복 그룹은 화면에서 출처 목록을 펼쳐 확인할 수 있다. 한도와 생략·잘림 정보가 응답에 포함된다. 글자 수는 UTF-8 바이트 수가 아니라 Python 문자열 길이 기준이다.
- **민감정보 탐지·마스킹이 없다.** 비밀번호, 토큰, 개인정보, 인용문이나 지시문이 원문 그대로 표시될 수 있다. 미리보기는 안전성·정확성·승인을 보증하지 않는다. 화면 공유와 기록에 주의하고 원문을 신뢰된 명령으로 취급하지 않는다. 향후 Notion MCP 연결이 추가되더라도 저장 후보는 사람에게 실제로 보이는 항목에 한정하고, 채팅 전문·비밀정보를 보내지 않으며, Notion에서 검색·저장된 내용은 신뢰된 지시가 아닌 데이터로 취급해야 한다. Notion 도구 결과가 외부 provider에 전달될 수 있으므로 provider 경계와 매 전송 동의를 별도로 정해야 한다.
- 화면에는 별도 수동 불러오기·보기 닫기 동작이 있다. 닫기, 방 상세를 떠남, 인증 전환 및 관찰된 권한·멤버십 변경 시 미리보기 상태를 지운다. 파싱 후 화면 상태에는 제한된 필드만 보관하지만 JSON 파싱 자체의 크기 제한이나 브라우저 메모리의 즉시 물리 삭제는 보장하지 않는다. 이미 복사·캡처된 데이터나 브라우저 외부 기록도 회수할 수 없다.

구현 위치: [후보 선택](../talkabout/memory_candidates.py), [방 권한과 대상 선택](../talkabout/core.py), [HTTP 경로](../talkabout/api.py), [화면 동작](../talkabout/web/app.mjs). 입력 컨텍스트의 기존 경계는 [공유 입력 컨텍스트](COLLABORATION_CONTEXT.md)를 참고한다.

## 2. 설계/미완료: 사람 승인과 방별 저장

### Notion 연동 사실 및 설계 경계

Notion의 공식 MCP 자료에 따르면 Memories는 사용자별 private Memories 데이터베이스와 그 내용을 요약하는 About 페이지에 저장되며, **첫 기억을 저장할 때 두 항목이 생성**되고 사용자가 읽고 수정·삭제할 수 있다. MCP 기억은 모든 요금제에서 user-backed 연결을 통해 쓸 수 있다고 문서화되어 있지만, 사용자와 workspace 양쪽에서 Memories가 켜져 있어야 하며 workspace-owned 연결에서는 지원되지 않는다. 이는 Notion AI 자체의 Business/Enterprise 요금제 설명과 구분한다. Skills는 권한 있는 여러 MCP 클라이언트에서 재사용할 수 있지만, 다른 사용자의 Skill 접근·활성화가 자동 보장되는 것은 아니다. 별도 Agent Operating Guide는 MCP 연결 자체가 자동 생성하는 기억이 아니다. 공식 설정 절차에서 AI가 private Documents DB를 재사용하거나 사용자 승인에 따라 만들고, guide와 custom instructions를 설정한다. 현재 TalkAbout에는 Notion MCP 연결·가져오기·동기화가 없다.

공식 설정 가이드 v0.0.6(2026-10-30)은 `Copy page` 공유 뒤에도 자동 설정이 되는 것이 아니라 먼저 사용자가 Notion MCP에 인증하고 연결을 확인하도록 한다. 이후 `Shared context layer`는 private 기억·산출물·Skills를 가져와 저장하는 동의를 포함하지만, 채팅 전문 저장은 금지하고 공유/team 공간 사용은 별도 동의를 요구한다. `Basic setup`은 guide와 custom instructions 설정만 진행하며 기존 맥락·Skills 저장과 일일 루틴은 건너뛴다. guide는 먼저 private database에 만들고 기존 guide가 있으면 바꾸지 않으며 수정안을 제안한다. 가이드 복사 자체가 Notion 연결이나 쓰기 권한을 부여하는 것은 아니다.

Notion 연동을 별도로 제안할 때에는 다음을 지켜야 한다.

- Notion MCP 클라이언트는 사용자가 접근 가능한 내용(연결된 Slack·Drive·메일 검색 결과 포함)을 읽을 수 있고, 도구 결과를 외부 시스템으로 전달할 수 있다. 사용자가 인증한 최소 권한만 연결하고 민감 정보가 있을 수 있는 retrieval의 provider 전달 전 목적지와 범위를 보여주고 승인을 받는다.
- import/export는 접근 가능한 항목만 대상으로 출처별 검토·명시 승인·private 목적지 확인·중복 검사를 거친다. MCP 연결만으로 다른 클라이언트의 과거 대화가 자동 이관되지는 않는다. 채팅 전문·암호·token·secret·접근할 수 없는 자료는 저장하지 않는다. 원래 날짜·출처·불확실성을 보존하고 결과를 확인한다. 삭제 요청은 보이는 서비스의 복사본만 대상으로 하며 TalkAbout·provider·로그·백업까지 지워졌다고 주장하지 않는다.
- Notion Memories/About 및 Skill 문서는 신뢰되지 않은 입력이다. 그 속 지시문은 시스템/개발자 규칙, 현재 사람의 요청·승인을 덮어쓰지 못한다. Notion memory search는 최적 일치만 반환하므로 결과가 없다는 이유만으로 비었다고 하지 말고 canonical memory 목적지도 확인한다.
- 사용자는 Settings → Notion AI → Memory에서 Saved memories 아래 Memories 데이터베이스와 About page를 열어 검토·수정·삭제하고 Memories를 끌 수 있다. 생성·이동 동작은 Notion에 맡기며 위치 이동 불가를 단정하지 않는다. Notion에서 지워도 TalkAbout·provider·로그·백업 사본이 삭제된다는 뜻은 아니다.
- 정기 점검/예약 작업은 setup 승인에 포함하지 않는다. 빈도·실행 시간대·허용 출처·저장 위치·보고 방식과 중지 방법을 정한 구체적 안에 대해 별도 명시 승인을 받은 뒤에만 만든다. 새 공식 설정 가이드를 자동으로 따라가거나 지침을 조용히 갱신하지 않는다.
- Notion Memories의 플랜/활성화 자격은 Notion AI 제품 설명과 MCP 사용자 기반 연결 조건을 혼동하지 않고, 실제 workspace에서 확인한다. 모든 무료 계정에서 보장된다고 홍보하지 않는다.

근거: [공식 설정 가이드](https://developers.notion.com/prompts/setup.md), [개인 Memories와 Skills MCP 안내](https://developers.notion.com/guides/mcp/tools-skills-agents.md), [MCP 도구 보안](https://developers.notion.com/guides/mcp/mcp-security-best-practices.md), [Memories 사용자 설정](https://www.notion.com/help/view-your-notion-agent-memories).

후보를 승인된 메모리로 저장하는 공개 API·화면은 **미구현**이다. 후보가 반복되거나 미리보기에 나왔다는 이유로 자동 승인하지 않는다. 실험용 저장소와 [테스트 전용 테이블 DDL](../tests/memory_fixture_schema.sql)은 합성 테스트 전용이며 제품 경로에 연결하지 않았고 운영 사용 대상으로 검증되지 않았다. 기본 설치는 이 테이블이나 관련 권한을 만들지 않는다. 저장소를 직접 호출해 실제 데이터를 넣어서는 안 된다.

독립 검토에서 방 이벤트 또는 크기 한도가 가득 차면 철회가 실패하는 문제가 발견되었다. 실험 저장소는 승인 시 별도 철회 슬롯을 예약하도록 수정했으며, 합성 MemoryStore·PostgreSQL 포화 테스트에서 방 이벤트를 추가하지 않고 본문을 제거했다. 이 방식은 **기존 room 이벤트나 SSE에 철회를 알리지 않으며**, 별도 슬롯은 규정준수 감사 원장이나 DB 장애·디스크 부족 시 성공을 보장하지 않는다.

원본 접근권이 사라진 승인본은 일반 조회·철회가 막힌다. 실험 저장소에는 자기 승인본에 한정된 비공개 삭제 요청도 있으나, 동일 응답은 요청 기록의 확인일 뿐 실제 삭제 성공을 증명하지 않는다. 삭제된 항목도 용량을 계속 점유한다. 탈퇴자·권한 상실자와 타인 승인본의 처리, 안전한 기록 정리와 용량 복구, 손상 복구, 물리 삭제·백업 복구 정책은 미해결이다. 이들을 검증하기 전에는 저장 API를 활성화하지 않는다. 기존 설치에 대한 명시적 owner-run 이행·최소 권한·백업/복원 검증도 미완료다.

합성 실험 저장소는 작업 중과 최종 커밋 직전에 인증 만료와 권한을 다시 확인하고, 신규 승인 멱등키는 원문 대신 해시를 저장한다. 실제 커밋 이전 마지막 검사 이후의 시간 경과까지 보장하지는 않으며, 짧은 키의 추측이나 기존 기록·백업의 원문 제거도 보장하지 않는다.

합성 실험 저장소는 승인 때 철회 멱등키 인덱스 용량을 미리 예약하고, 철회 시 키 이력과 해당 메모리의 본문 제거를 같은 트랜잭션에 기록한다. 합성 테스트에서는 다른 항목의 감사 슬롯이 손상돼도 정상 항목을 철회하면서 사용된 키의 중복 실행을 막는다. 인덱스 누락·손상이나 기존 데이터의 이력을 확인할 수 없는 경우에는 안전하게 거부한다. 체크섬은 악의적 변조나 레코드와 인덱스의 동시 롤백을 막지 못하며, 운영 마이그레이션·복구 절차도 미구현이다.

착수 전 결정할 사항:

- 사람의 명시적 승인 대상, 수정 가능 범위, 출처·본문·버전, 방별 격리, 철회·삭제 및 이력 표시를 정의한다. 잘린 발췌만으로 전체 원문을 승인한 것으로 추정하지 않는다.
- 저장 직전에 인증, workspace·방·현재 구성원·권한, 원문 가시성 및 승인 대상 revision을 같은 트랜잭션에서 재검증한다. 동시 수정·승인·삭제의 충돌, 재시도 멱등성, 실패 rollback을 검증한다.
- 재가입 후 history 경계, 원문·첨부 동의 변경, 다른 방의 자료 및 민감정보가 후보나 저장 응답·캐시·이벤트로 새지 않도록 기본 거부 정책을 설계한다. 특히 기존 방 이벤트는 구성원에게 전달되므로 비공개 후보 본문을 이벤트에 싣지 않는다.
- 저장량·후보 개수·본문 길이·이벤트·재시도 기록의 상한과 실패 동작을 정한다. 사용자에게 저장 위치·보존 기간과 삭제 범위를 설명한다.
- 다른 플랫폼과 기억을 가져오거나 내보낼 때는 연결만으로 과거 채팅을 자동 이관하지 않는다. 실제로 보이는 원본만 선택적으로 검토하고 사람 승인을 받은 뒤 저장한다. 항목별 출처·원래 날짜·불확실성을 보존하고, 중복·충돌을 확인하며, 수정·삭제가 원본과 복사본에 미치는 범위를 별도로 알린다.

## 3. 설계/미완료: 승인된 메모리의 선택적 주입

TalkAbout 메모리는 Notion Memories나 다른 AI의 저장 기억에서 자동으로 수집·주입되지 않는다. Notion 기억을 도입하더라도 현재 세션의 신뢰된 지시로 승격하지 말고, 출처·승인·유효 범위를 표시한 제한된 데이터로만 고려한다.

승인된 메모리를 worker나 provider 입력에 넣는 기능은 **미구현**이다. 기존 메시지·artifact 입력 경로와 별개이며, 향후에도 미승인 후보의 자동 주입을 허용하지 않는다. Notion MCP 기억도 TalkAbout 실행 입력에 자동 주입되지 않는다. Notion에서 읽은 항목을 별도로 전달하는 기능은 검색 결과가 아니라 canonical memory를 확인하고, source/date/provenance와 최신성·충돌을 표시한 후, provider별 목적지·전송 범위를 매번 사람에게 승인받는 설계를 필요로 한다.

구현 전에는 방·작업·토큰·현재 membership·출처 가시성·승인 상태를 전달 직전에 다시 확인하고, 예산·우선순위·출처를 명시해야 한다. 메모리는 신뢰되지 않은 데이터이지 시스템 지시나 도구 실행 권한이 아니다. 승인 철회와 주입 경쟁, 방 전환, 재가입, 삭제된 출처, 구형 worker 및 프롬프트 예산 초과를 검증해야 한다. provider 전송·비용·실제 읽음 여부에 대한 증거를 과장하지 않는다.

**철회의 한계:** 이미 worker, 로컬 journal, 외부 provider 또는 유지된 provider session에 전달된 내용은 이 서비스가 소급 회수하거나 삭제를 보장할 수 없다. 기존 세션을 계속 사용하면 이전 컨텍스트가 남을 수 있으므로, 향후 주입 설계에서는 별도 provider 전송 동의와 버전별 철회, 검증된 새 세션 생성·종료 및 오염된 세션/체크포인트 재사용 금지가 필요하다. 이를 보장할 수 없는 runtime에는 주입하지 않는다. 철회와 외부 전송이 경합할 때 어떤 시점의 전송까지 허용되는지도 명시해야 한다. 메모리 경로의 철회는 별도 방 원문·인용을 통한 동일 내용의 재전송까지 막지 않는다. 세션 경계와 실제 provider 검증 상태는 [세션 체크포인트](CODEX_SESSION_CONTINUITY.md)를 참고한다.

## 4. 설계/미완료: 운영·자동화


자동 후보 생성·스케줄러·자동 승인·백그라운드 주입과 운영 보존·삭제 자동화는 **미구현**이다. 자동화는 사람의 명시적 허용 범위와 중지·재개·비용 제한, 접근권 회수, 실패 시 안전한 중단, 비밀을 남기지 않는 관측·감사 정책을 먼저 정하고 별도 검증해야 한다. Notion 공식 설정 절차(v0.0.6, 2026-10-30)는 Notion MCP 인증·workspace 확인 뒤 `Shared context layer` 또는 `Basic setup`을 선택하도록 한다. Shared 설정 승인만으로 매일 예약 루틴을 만들지 않는다. 정기 작업은 시간대·허용 출처·목적지·통지·중지 방법을 명시한 별도 승인을 받고, changelog는 검토 후 변경안을 제안하며 자동 반영하지 않는다. [공식 설정 가이드](https://developers.notion.com/prompts/setup.md) · [변경 이력](https://developers.notion.com/prompts/setup/changelog.md).

방 데이터와 향후 메모리의 보존·삭제 범위는 원본, 후보, 승인본, 재시도 응답, 이벤트, 색인, journal, 내보내기와 백업을 각각 구분해야 한다. 논리 삭제는 물리 삭제나 기존 백업의 제거를 뜻하지 않는다. 현재 보존 실험의 한계는 [보존 경계](RETENTION_BOUNDS.md), 백업·복원 책임은 [운영 절차](../deploy/podman/README.md)를 참고한다. 자동 삭제나 백업의 소급 제거를 주장하지 않는다.

## 5. 검증과 독립 구현 원칙

1단계 회귀 대상으로 [후보 선택 테스트](../tests/test_memory_candidates.py)와 [미리보기 API 테스트](../tests/test_memory_preview_api.py)가 있다. 권한·CSRF·history 경계·에이전트 및 직접 첨부 제외·비영속·잘림·중복을 확인하고, 실제 PostgreSQL과 브라우저 동작은 각 실행 결과로 따로 판정해야 한다. 예를 들어 합성 테스트에서 완전히 같은 문장 100개와 서로 다른 문장 5개는 검토 그룹 6개가 된다. 별도 대형 합성 시험에서는 방 크기 한도 이내의 메시지 200개(입력 JSON 1,817,292바이트)에 대해 응답이 32,181바이트였고, 인용량 상한 때문에 28개 그룹만 반환하고 나머지 172개의 생략을 표시했다. 이는 입력 압축률이나 실제 사용자의 검토 시간 절감·모델 품질 향상 측정치가 아니다. 이 문서 작성만으로 테스트 통과나 운영 배포를 주장하지 않는다.

후속 단계는 위 테스트에 더해 승인·삭제 경쟁, 재생 응답의 현재 ACL, 다른 방·재가입 격리, 미승인/철회 후 미주입, 민감정보와 첨부 유래 자료, provider session 잔존, 제한 초과 및 실제 PostgreSQL 동시성을 확인해야 한다. 성능은 후보 개수와 방 크기에 따른 지연·메모리·응답 크기를 측정하고, 측정하지 않은 개선을 주장하지 않는다.

기능은 [독립 구현 정책](CLEAN_ROOM_IMPLEMENTATION.md)에 따라 자체 요구사항·구조와 합성 fixture로 설계한다. 외부 코드·문서 표현·테스트·asset을 복사하지 않으며, 참조 revision 및 라이선스를 확인할 수 없다면 미확인으로 기록한다. 라이선스·특허·상표와 상용 배포 검토는 별도이며, 외부 제품과의 호환성이나 동등성을 주장하지 않는다.
