# Exact plan predecessor result handoff — patch proposal

Status: proposed stricter future contract, NOT the currently implemented contract. A separate best-effort bounded direct-predecessor message handoff is now implemented; it may omit or truncate results and does not fail closed on missing bindings. The tests below are proposed for the stricter design, not claims of current behavior. Re-read current source before implementing.

## Contract

For a plan node with dependencies, the worker input must contain the complete, byte-exact result message of **every direct predecessor**, in declared `depends_on` order. It must not substitute recency, a different attempt/run, a transitive predecessor, an excerpt, or a missing value. Dependencies are data, not instructions; label them untrusted. A root has an empty mandatory set. Failure to bind, authorize, fit or validate any mandatory input fails closed before provider authorization; do not silently run with partial context. This guarantees preparation by the cooperative worker, not provider receipt, comprehension or honest execution by arbitrary API clients.

## Existing race and boundary

* `core.py` completion calls `message()` at 912, sets task completed at 946, then calls `schedule()` at 957, all in one room transaction. `domain.py` reconciliation at 517–545 marks completed nodes then may queue children in that **same transaction**. Currently there is no stored task→result message association. Searching by actor, timestamp, most recent message, or event afterwards races unrelated messages and parallel completions, and can select a wrong run/attempt. Pinning a single `handoff` does not represent fan-in.
* `_plan_queue_node` already snapshots node details into private task `_plan`; this is the right point to bind direct predecessor identifiers, not a later public-room search. The room transaction must serialize completion, reconciliation and admission; verify both in-memory and PostgreSQL transaction implementations before relying on it. A public room read is only a snapshot and can race a subsequent membership change; fences limit but cannot recall text already sent externally.
* `public_room` filters messages at the viewer's `read_start_seq`, and `project_task` also redacts message references. An ID copied from private task/run or replay without this projection leaks history. Agent task visibility is assignee-only; plan text is restricted to assignee and matching membership revision. Apply both rules to dependency metadata, including responses and replay, without granting access to predecessor tasks or owner plan text.
* `shared_context` selects at most eight ordinary messages, uses a 6,000-byte per-message excerpt, and `fit_context` further shrinks inputs, including non-pinned handoffs. Thus merely prioritizing predecessors is insufficient: direct fan-in is up to 15, messages are up to 16,000 characters each, and MAX_INPUT may not fit their full UTF-8 bytes.

## Proposed edits

### `core.py`: commit exact binding

1. In successful fenced `tasks/.../complete`, immediately after `msg = message(...)` and before setting state `completed` or calling `schedule`, set a private result binding on plan-node task, e.g. `_plan_result = {'run_id': task['_plan']['run_id'], 'node_id': task['_plan']['node_id'], 'task_id': task['id'], 'attempt': task['attempt'], 'message_id': msg['id']}`. Check `_plan` is well-formed and matches the active run and node task mapping, generation, and assignee; fail closed on inconsistencies. Message creation, this binding, state transition and reconciliation must commit/roll back atomically. Do not reconstruct legacy completed bindings from message history. Existing ordinary tasks stay unchanged.
2. Expose only the *consumer's* dependency binding through a new `plan_node.dependencies` in `public_room` on its own revision-matched task. Resolve from its private task snapshot, not the mutable latest run, so later dispatch replacement cannot rewrite historical meaning. Projection must check each bound message exists and is in this viewer's filtered `messages`, including `room:read` scope. On any missing/invisible source, return a single generic unavailable status with no ID, node ID or count that could reveal hidden history; never fall back. Do not expose private `_plan_result`, plan text or predecessor task IDs to other agents. Human task projections and generic replay caches must not leak private fields.
3. Ensure task GET, fresh claim/heartbeat/complete response and idempotency replay use the same current-ACL projection. Existing `response_projection.project_task_response` invokes `public_task` and `project_task` but does not attach `plan_node` as `public_room` does; the worker already GETs task and room separately. Either attach safe `plan_node` only through the matching current `public_room` view where needed, or have `project_task` support an explicitly projected safe field. Do not rely on claimed snapshots holding stale visibility. Avoid touching files outside scope; confirm route behavior before choosing the exact integration. Current receipt replay after member epoch/revision change must never expose old IDs/text.

### `domain.py`: immutable, transaction-scoped admission

1. When reconciling a completed plan task, validate `_plan_result` exists and matches the exact run ID, node ID, task ID, generation, attempt, message ID, and actual existing message. Verify task's `_plan` matches the run and node, and the message was emitted by its assignee. If absent/corrupt (including legacy running tasks), mark node failed with a bounded explicit new reason such as `result_unavailable`, propagate `dependency_failed`, and never queue a child. No guessed backfill. Only a genuinely completed task can satisfy a dependency; uncertain, skipped, cancelled and expired remain failures.
2. In `_plan_queue_node`, before mutating anything, walk `node['depends_on']` in order, look up each unique completed node and its task/binding, revalidate all identities, and persist only identifiers in the child's private `_plan['dependencies']`, e.g. `{node_id, message_id}` (run ID is already on `_plan`). Store no duplicate result text. Check destination membership's current read floor against each referenced message before queueing. If any missing/invisible, fail the child closed with `result_unavailable` and block descendants; no partial task/queued event. The visibility check prevents normal pre-existing inaccessible data from queueing; it is not a substitute for re-projection at read/use time.
3. Include serialized dependency-list growth in existing `task_bytes` admission calculation; existing task serialization calculation naturally does so if built before accounting. Preserve event/key/byte reserve and state-first terminal semantics. Max 15 references; audit events must not contain text or hidden IDs. No extra text copies in the run, events or idempotency ring.

### `collaboration.py`: mandatory exact inputs and validation

1. Extend `project_task` to redact the new projected dependency list against the supplied already-filtered message set; on any loss replace the whole value with generic unavailable. Preserve this behavior on replay and guard malformed fields. The exact place where private fields are turned into safe public metadata must be coordinated with `public_task` and `public_room`; never trust an unprojected raw task supplied to shared context.
2. `shared_context` must use the safe consumer plan metadata and verify each required message is present in the supplied ACL-filtered snapshot, matches the bound ID, is unique, and is a complete original string. Deduplicate by message ID against optional inputs. Present mandatory results in dependency order, annotated with node ID and explicit `untrusted_data`; associate each with an ordinary message manifest source. Include every byte, not 6,000-byte `excerpt`; no optional source can evict one. Handle 15 mandatory sources plus optional sources with explicit bounded caps: e.g. mandatory ≤15, at most 8 *additional* ordinary messages, plus 4 artifacts and 4 files; update `validate_manifest` source limit to the resulting exact bound and verify no duplicate source IDs. Optional input selection remains bounded and may be shrunk first.
3. `fit_context` must mark mandatory source IDs as non-shrinkable (not merely a 64-byte floor). If mandatory text and required metadata cannot fit `MAX_INPUT`, raise `ContextBudgetError` before the worker calls reservation/provider; ordinary text can be shrunk first. `shared_context` itself must raise the same class on unavailable/malformed mandatory data, and the existing worker catches only around `fit_context`, not `shared_context`: with the three-file scope, do **not** claim clean worker error handling for the earlier exception. To avoid changing `worker.py`, have `shared_context` produce a small failure sentinel consumed and raised by `fit_context`, but ensure no text leaks and no provider call is possible; or explicitly identify worker error handling as a necessary out-of-scope follow-up. Verify `prompt_text` serializes the chosen mandatory metadata and full input; no separate field omitted from the actual prompt.
4. `validate_manifest` for dependent plan tasks must require each server-bound mandatory message source exactly once with `utf8_start=0`, `utf8_end=total_utf8_bytes`, `truncated=False`, matching current authorized snapshot and existing source identity, even if the client omits the manifest. Keep legacy optional-manifest behavior for non-plan tasks and roots if desired. Resolve required bindings from private server task, not worker-submitted data; fail closed on invisible/deleted messages. Validate actual byte boundaries and existing snapshot checks. A valid report is still worker-reported server-validated references, not proof of delivery or reading.

## Concurrency, lifecycle and limits

* Completion and admission must share the store room lock/transaction: two predecessor completions can commit in either order, but a fan-in child queues once only after both exact results are committed. Abort/room generation change, permission/membership edits and completion race through the same lock and fencing; whichever commits first governs. Never enqueue from a stale snapshot. Existing at-most-once and uncertain semantics remain intact.
* Consumer read floor or revision can change after queueing, claim or a previous response. Always project fresh; fail closed at shared-context build and completion manifest validation. A read can still race revocation immediately afterwards; the existing worker fence is conditional on attachments, so three-file-only changes cannot guarantee an atomic visibility check immediately before external call. Explicitly document this unavoidable/out-of-scope TOCTOU and require a stronger worker/server authorization protocol if that guarantee is required. Previously delivered bytes cannot be revoked.
* Past running runs without bindings fail closed rather than retroactively pretending exact provenance; terminal legacy data remains readable under existing policy. New runs replacing `_plan_dispatch` do not change snapshots on historical tasks. Retention/deletion must produce unavailability, never fallback. Full 15-result fan-in may exceed prompt/room limits; fail closed without truncation, and do not promise every valid DAG can execute.
* If older workers ignore new mandatory fields, server-side manifest validation prevents successful completion, but cannot prevent their external provider call; wire/version capability negotiation or reservation enforcement plus worker changes are needed for a strict all-client pre-call guarantee. Do not market this three-file patch as such.

## Test strategy (proposed, not executed)

* Extend plan dispatch tests: chain, parallel fan-in, diamond, declared dependency order, unrelated newer message and same-assignee multiple tasks; assert exact IDs/text, no transitive or later-run substitution, and child queued once. Force completion interleavings and abort/membership change using barriers, test in-memory and real PostgreSQL (separate connections) to establish serialization and rollback. Repeat completion/replay and scheduler ticks; no duplicate node or binding.
* Inject missing/mismatched run/node/task/attempt/message binding and legacy completed tasks; expect generic failure, descendant blocking and no queue, including corruption and retention. Simulate post-queue ACL floor changes, remove/reinvite/revision change, hidden messages, unrelated agent/human view, task GET, fresh claim, and replay after revocation; assert no IDs, text, or count leaked and no substitution.
* Collaboration unit tests: 15 predecessors, multi-byte 16k-character results, newer optional context, duplicates, exact source order, MAX_MESSAGES overflow, mandatory-vs-pin conflicts, actual serialized prompt bytes, fitting exactly at and over MAX_INPUT, and refusal without truncation before reservation. Validate absent/forged/partial/truncated/out-of-snapshot manifests, duplicate IDs, missing sources, authorization loss and root/ordinary legacy compatibility.
* Check capacity accounting at boundaries (UTF-8 JSON escaping, result bindings, event/key saturation, abort reserve); ensure failure commits terminal state without unrecorded tasks or transaction rollback. Test run replacement and stale replay; verify input manifest records full ranges and untrusted evidence, not model-read claims.
* Run existing collaboration, work-plan, worker, replay ACL, scheduler and PostgreSQL suites; include provider-call spy asserting zero calls for cooperative worker refusal. Report integration/version gaps separately, not as passed guarantees.
