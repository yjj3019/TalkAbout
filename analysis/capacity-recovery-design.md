# 용량 포화 복구 설계 초안 — 명시적 보관과 사람 승인

## 상태와 범위

**설계 제안이며 구현·배포된 기능이 아니다.** 목적은 이벤트/방 바이트 상한에 막힌 방을 기록 손실이나 중복 실행 없이 복구하는 것이다. 운영 데이터 삭제, 자동 cleanup, 운영 DB 접근은 수행하지 않았다. 현재 제품에는 운영 archival·paging·삭제 정책이 없고 `compact_fixture`는 합성 테스트 전용이다. 기존 기록을 자동으로 삭제하거나 이 함수를 운영용으로 전용하지 않는다.

## 1. 분리해서 진단할 용량

| 용량 | 현재 개발 상한·특징 | 복구 시 유의점 |
|---|---|---|
| retained events | 방당 2,048건; dispatch 시작에는 추가 여유가 필요 | 승인된 이벤트 prefix 보관·제거로 회복할 수 있으나 느린 소비자에게 gap 발생 |
| room 직렬화 바이트 | 2 MiB; 실행 중 계획에는 추가 예약 공간 | 이벤트뿐 아니라 메시지·task·artifact·keys 등도 차지. 이벤트만 비워도 해결되지 않을 수 있음 |
| task | 방당 256건 | 이벤트 제거와 무관. task 상태와 실행 증거 보존 정책 별도 |
| idempotency keys | 방당 2,048개, 실행 중 계획은 별도 여유 | 키·digest·epoch tombstone 삭제는 오래된 요청 재실행 위험. 별도 설계 전 삭제 금지 |
| cursor/worker journal | 별도 수명·개수·로컬 용량 | 방 이벤트 보관으로 worker journal 용량이 회복되는 것은 아님 |

각 진단은 현재 사용량, 적용 상한, 실행 중 예약 여유, 예상 회복량을 각각 표시한다. 조회 자체는 인증·room:read 검사를 거치며 상세 백업/복구는 owner의 room:control과 별도 운영 권한을 검토한다. 저장 가능한 이벤트를 요구하지 않는 상태 조회 경로가 필요하다.

## 2. 복구 흐름

1. **진단**: 방별 포화 원인과 어떤 데이터 종류가 공간을 사용하는지 사람이 조회한다. 삭제 가능한 항목을 추정하지 않는다. 서버가 만료나 시작된 외부 호출을 확인하는 동안 신규 작업은 계속 fail-closed한다.
2. **계획 생성 — 읽기 전용**: 방 ID, generation, membership epoch, event floor, 마지막 seq, 제거 제안 범위 `[first_retained_seq, cutoff_seq]`, 개수와 예측 크기를 제시한다. 범위는 연속 prefix만 허용한다. 계획에는 짧은 유효기간, 불변 fingerprint, 현재 데이터 revision을 포함한다. 이 단계는 데이터를 변경하지 않는다.
3. **보관본 생성**: 권한 있는 운영자가 서버 외부의 승인된 저장 위치에 내보낸다. 이벤트 원문, seq 범위·개수, 방 식별자, schema/export 버전, 생성 시각, 해시를 포함한 manifest가 필요하다. 비밀 정보 포함 가능성을 표시하고 접근 제어·암호화·보존 기간·백업 책임을 별도 정책으로 정한다. 해시는 무결성을 증명할 뿐 저장소의 내구성이나 권한을 증명하지 않는다.
4. **검증 및 승인**: 보관본을 다시 읽어 범위·연속성·개수·해시를 확인한다. owner는 구체적인 범위와 gap/복구 영향, 보관본 식별자, 남는 용량, 복구 불가능한 위험을 확인하고 명시적으로 승인한다. 백업 및 승인 권한과 2인 승인 필요 여부는 미결정이다.
5. **원자적 적용**: 방 단위 잠금을 잡고 계획의 fingerprint, epoch/generation, floor, cutoff, 보관 검증 증거와 권한을 다시 확인한다. 새 이벤트가 뒤에 추가되었더라도 승인된 prefix의 내용이 같고 다른 전제조건이 유지될 때만 적용하는 정책을 명시적으로 결정한다. 이벤트 prefix 삭제와 `first_retained_seq = cutoff + 1`, 보관 manifest 참조, 감사 메타데이터는 같은 트랜잭션에 기록한다. `last_seq`는 절대 감소·재사용하지 않는다. 실패하면 전부 rollback한다. MemoryStore도 동등한 lock/copy/commit 의미를 제공해야 한다.
6. **재동기화 및 복구 확인**: 유효한 커서가 새 floor보다 뒤처졌다면 누락 없이 `cursor_gap`을 반환한다. 승인된 snapshot rebase에서 gap을 명시하고 ACL·epoch·generation을 다시 검사한다. 재동기화한 커서가 누락 구간에 대한 수신 확인으로 오인되지 않도록 기존 `skipped_rooms` 방침을 유지한다. worker는 snapshot에서 자기 task의 claim/lease/reservation을 재검사한다. started/uncertain 호출은 자동 재시도하거나 완료로 추정하지 않는다.
7. **후속 진단**: 실제 바이트·task·키 사용량을 다시 측정한다. 해결되지 않았다면 원인을 분리해 표시하고 계속 보류한다. 이벤트 제거 후에도 자동 복구를 보장하지 않는다.

## 3. 일관성·보안 불변식

- 삭제 전에 **검증된 보관본 + 해당 범위에 대한 명시 승인**이 필요하다. 승인 없는 자동 삭제·자동 재시작 금지.
- `last_seq` 단조 증가, 연속 prefix만 제거, floor의 원자적 갱신. 이벤트 중간 구멍은 허용하지 않는다.
- 현재 이벤트 조회는 방 floor snapshot과 이벤트 행 조회가 분리돼 있어, 동시에 prefix를 제거하면 누락을 조용히 건너뛸 위험이 있다. 구현 전 같은 일관된 읽기 스냅샷/락 또는 floor 재검증으로 해결해야 한다. SSE·MCP·브라우저·worker 모두 410/gap와 명시적 rebase를 검증한다.
- 메시지·artifact 원본, task, membership epoch, 권한, idempotency tombstone, worker journal, cursor와 실행 예약은 이벤트 정리의 대상이 아니다.
- 완료되지 않은 task의 실행 증거와 uncertain 외부 호출은 보존한다. 복구 과정은 provider 호출을 시작하지 않는다.
- 압축 경로는 idempotent하고 중복 승인·stale 계획·권한 상실·보관 검증 실패·중단/재시도에 fail-closed한다. 잘못된 범위나 수정된 해시를 거절한다.
- 제어 plane 상태 및 승인 증거에 사용할 공간이 이미 소진됐을 수 있다. 같은 포화 room payload 또는 이벤트 ring에만 의존하지 않는 별도의 제한된 내구성 저장 경로가 필요하며, 인증과 트랜잭션 설계는 별도 검토한다.

## 4. 메시지·task·키 등으로 인한 바이트 포화

이벤트 보관만으로 일반적인 2 MiB 포화는 해결되지 않는다. 데이터 종류별 보존·조회·백업·복원 정책이 결정되기 전 메시지, artifact, task 및 키 tombstone을 삭제하지 않는다. 다음 단계는 원본을 보존하는 외부 저장/페이지화 설계와 마이그레이션, 이전 cursor·검색·권한 경계의 호환성 검증이다. 당장 안전한 수동 우회는 기존 방을 보존한 상태에서 사람이 새 방을 만들어 필요한 문맥을 명시적으로 인계하는 것이지만, 방 수 상한과 새 방의 권한·세대·진행 중 작업에 유의해야 하며 자동 연속 실행을 뜻하지 않는다.

## 5. 구현·검증 순서

1. 포화 원인별 **읽기 전용 진단**과 owner UI. 민감 정보 및 소진된 payload의 한계 검증.
2. 운영 정책 확정: 보관 위치·접근 권한·암호화·보존 기간·승인자·삭제 허용 범위·복원 책임.
3. 실제 삭제 없는 내보내기/manifest/무결성 재검증과 실패 주입 테스트.
4. 일관된 이벤트 조회와 gap/SSE/MCP/worker rebase 수정 및 동시성 테스트.
5. 별도 승인된 prefix 정리 API: row lock, stale 계획 거절, atomic floor/delete, 감사 기록, crash/restart·재실행 테스트. Memory와 격리 PostgreSQL에서 parity 검증.
6. 별도 설계로 메시지·task·키 등 바이트 포화를 해결한다. 저장 계층/마이그레이션/개인정보와 백업 보존 정책을 검토한다.

실제 운영 데이터나 provider를 사용하기 전 synthetic fixture에서 다중 읽기·쓰기 경합, 느린 cursor, 재시작, 보관 손상, 권한 변경, 승인 replay, uncertain 작업, byte/event/task/key 포화 조합을 검증한다. 외부 스토리지 장애 시 삭제하지 않는 것도 확인한다.

## 6. 아직 필요한 사람의 정책 결정

- 보관본의 위치·암호화·접근자·보존 기간·복원 시험 책임.
- 이벤트 삭제 최소 보존 기간, 삭제 가능한 이벤트 종류, 감사를 위한 법적·조직적 요구사항.
- 승인 주체와 2인 승인 필요 여부, 사전 백업 및 복원 검증 기준.
- 클라이언트 gap 허용·알림·운영자 조치와 종료된 방의 수동 인계 정책.
- 메시지·task·artifact·키 tombstone 등 이벤트 외 저장량의 별도 장기 보존 정책.
