## 2. artiboard 1.23.7 — 신뢰성 결함 6건 (`8e394b4`)

커밋 메시지가 고친 결함 6개를 TalkAbout 코드에 대입했다.

| # | artiboard의 결함 | TalkAbout 대조 | 조치 |
|---|---|---|---|
| 1 | Supabase 읽기가 `max_rows`(1000)에서 **조용히 잘림** | **해당·부분 반영.** `store.py`의 `tick_all`은 활성 방을 `LIMIT 65`로 읽고 64개 초과면 `scheduler_capacity`로 **틱 전체를 실패**시켰다(잘림이 아니라 전면 중단). 같은 틱에서 한 소유자가 principal 128개를 넘겨도 모든 방이 멈췄다 | **반영함**: 64개씩 keyset 페이지로 읽고 총 상한을 1024로 명시, 429 용량 거절은 **그 방만 건너뛰고** `/health`에 `skipped_rooms` 표시. 상한 초과는 조용히 자르지 않고 명시적 오류 |
| 2 | 연결이 끊긴 사이 **삭제를 놓침** | TalkAbout 이벤트는 append-only이고 cursor 재조회로 복구(문서 `ARCHITECTURE.md`·`API_DRAFT.md`). 삭제 의미가 있는 경로(멤버십 purge 등)는 코드로 재검증하지 않았다 | 변경 없음. `[unverified]` |
| 3 | 꽉 찬 "최신 N개" 창에서 행이 빠지면 다음 행을 안 읽음 | 웹 UI의 제한 목록(`app.mjs`)은 이번에 읽지 않았다 | 변경 없음. `[unverified]` |
| 4 | 작업 완료 시 의존 작업을 **200개까지만** 해제 | TalkAbout work plan의 노드 수 상한은 `validate_work_plan`이 정한다. 이번에 그 상한과 해제 로직을 다시 읽지 않았다 | 변경 없음. `[unverified]` |
| 5 | 소유자 보정(repair)이 **열 때마다** 실행되어 정당한 재배정을 되돌림 | `talkabout/schema.sql`에 `UPDATE`/`DELETE`/`INSERT` 구문이 **없다**(grep) — 열 때마다 도는 데이터 보정이 없음 | **해당 없음**(확인) |
| 6 | 깨진 URL 요청이 처리되지 않은 rejection으로 서버를 멈춤 | FastAPI/uvicorn 경로. 직접 재현하지 않았다 | 변경 없음. `[unverified]` |

**남은 용량 절벽(미변경, 설계 결정 필요)**: `store.py`에는 소유자당 방 목록 `LIMIT 65`, principal `LIMIT 129`(`principal_list_capacity_paging_unsupported`)가 명시적 429로 남아 있다. 이는 조용한 잘림이 아니라 fail-closed지만, 한도를 넘는 소유자는 목록·진행이 막힌다. 해결하려면 API·UI 페이지네이션 설계가 필요해 이번 범위에서 바꾸지 않았다.

## 3. session-peer 1.5.0 — 공급망·CI 강화 (`d901230`, `3a1ca5e`, `9a0b23f` 외)

변경은 기능이 아니라 **릴리스·의존성 위생**이 중심이다: Dependabot 업데이트(검토 후 반영), **redacted 출력의 secret 스캔 워크플로**, 워크플로 액션 고정, MCP SDK 1/2 이중 호환 시험, 릴리스 문서화.

| 항목 | TalkAbout 대조 | 조치 |
|---|---|---|
| 액션 SHA 고정·`persist-credentials: false` | `safe-regression.yml`이 이미 SHA로 고정하고 `persist-credentials: false`, `permissions: contents: read`를 사용 | 이미 충족 |
| 의존성 제약 파일 | `.github/ci-constraints.txt` 존재 | 이미 충족 |
| **secret 스캔** | 없었음 | **반영함**: `.github/workflows/secret-scan.yml`(Gitleaks 8.30.1, SHA-256 고정, 전체 이력, `--redact`) + `.gitleaks.toml`. **예약·수동 실행만**(아래 한계 참고) |
| **Dependabot** | 없었음 | **반영함**: `.github/dependabot.yml`(pip·github-actions, 주간, 묶음, 열린 PR 3개 상한). PR만 열고 병합하지 않음 |
| MCP SDK 이중 호환 시험 | TalkAbout의 `mcp.py`는 MCP SDK를 쓰지 않는다(`json`·`re`·`sys`·`httpx`만 import) | 해당 없음 |

**한계**: Gitleaks 기본 규칙을 이 저장소 이력에 **로컬에서 돌려 보지 못했다**(내려받은 실행 파일의 실행이 자동 모드 분류기에 의해 거부됨). 시험 토큰·합성 값이 많은 저장소이므로 첫 실행에서 오탐이 나올 수 있다. 그래서 PR·push에서 막는 게이트로 만들지 않고 예약·수동으로만 두었다. 첫 결과를 사람이 읽고 필요한 허용 항목을 `.gitleaks.toml`에 추가한 뒤 게이트로 올린다. 바이너리 해시는 릴리스의 `gitleaks_8.30.1_checksums.txt`와 내려받은 파일을 직접 대조해 일치함을 확인했다.

## 5. 이번에 구현하지 않은 것과 이유

**P1 "제한된 후보 비교 모드"**는 이 요청의 "완벽한 반영" 범위에 넣지 않았다. R7이 스스로 "권고일 뿐 구현이 아니다"라고 한계를 정했고, 구현하려면 코드가 정할 수 없는 결정이 먼저 필요하다.

1. **대상 작업 유형과 평가기**: 안정적인 평가기가 있는 작업만 비교할 수 있다. 어떤 작업을 대상으로 할지, 평가기를 누가 소유하는지(에이전트가 고칠 수 없어야 함).
2. **예산과 승인**: 후보마다 모델 호출이 든다. 호출·비용 상한과 실제 공급자 사용 승인이 필요하다(현재 Codex 수명 시작 6/6 소진, Claude 3/3 — 10-25 기록 기준).
3. **격리**: 후보별 격리 worktree와 동시 실행 정책. 이번에 넣은 work profile git 전제가 그 선행 조건이지만, 후보별 격리 체크아웃·병렬 실행·비용 귀속은 별도 설계다.
4. **채택 권한**: 자동 선택을 쓰지 않고 사람 채택으로 둔다는 R7 원칙은 유지.

이 결정 없이 구현하면 R7이 명시적으로 금지한 "무한 루프·자동 채택·가격 없는 k 확장"에 가까운 것이 만들어질 위험이 있다.

## 6. 한계

- upstream 테스트·빌드·공급자 호출을 실행하지 않았다. artiboard의 테스트 추가(6건 가까이)와 session-peer의 SDK 계약 시험은 저장소에 있는 증거로만 읽었다.
- 변경 없는 5개 저장소는 이번에 다시 읽지 않았다. R7의 라이선스 판정(autoresearch LICENSE 부재, bloks FSL 등)도 그대로다.
- artiboard #2~#4·#6 대조는 TalkAbout 해당 코드를 이번에 정독하지 않은 항목이며 `[unverified]`로 표시했다.
- `tick_all` 페이지 처리는 가짜 연결로 논리를 검증했고 **실제 PostgreSQL에서는 실행하지 않았다**(CI의 임시 PostgreSQL 시험에서 확인해야 한다).
